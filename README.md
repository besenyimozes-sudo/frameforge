# FrameForge — browser-local MP4 fast-start optimizer

A Vite + React + TypeScript app inspired by modern creator video tools, with distinct branding. It performs a real MP4 container rewrite in the browser: if `moov` appears after `mdat`, it moves `moov` before media data and adjusts `stco` / `co64` chunk offsets. It does not transcode or re-encode media.

## Requirements

- Node.js 20 or newer
- npm
- A modern browser with `ArrayBuffer`, `Blob`, and File API support

## Run locally

```bash
npm install
npm run dev
```

Open the local URL Vite prints.

## Build

```bash
npm run build
npm run preview
```

The production site is static and can be deployed to Vercel.

## Deploy to Vercel

1. Create a Git repository and add these project files.
2. Push the repository to GitHub/GitLab/Bitbucket.
3. In Vercel, choose **Add New → Project** and import the repository.
4. Framework preset: **Vite**. Build command: `npm run build`. Output directory: `dist`.
5. Deploy. `vercel.json` rewrites app routes to the SPA entry point.

You can also use the Vercel CLI from this folder:

```bash
npm install
npm run build
npx vercel
```

## What is actually implemented

- Reads MP4/M4V files in the browser only. No video upload endpoint or server processing exists.
- Parses top-level ISO BMFF boxes and inspects `ftyp`, `moov`, `mdat`, duration, common codecs and sample dimensions.
- If the file is already fast-start (`moov` before `mdat`), validates and returns the source bytes as a new downloadable Blob.
- For supported non-fragmented files where `moov` trails `mdat`, moves `moov` immediately after `ftyp`, adjusts all `stco` and `co64` offsets by the relocation size, then reparses output to verify ordering.
- Encoded audio/video sample payloads are copied unchanged; this tool does not decode/re-encode media.
- Provides responsive UI, file inspection, errors, download and guide/FAQ sections.

## Important limitations

This is a conservative first version, not a universal MP4 repair tool. It expects one `ftyp`, one `moov`, and one `mdat` box, and rejects fragmented MP4 (`moof`). Very large files are loaded into memory in full, so the browser can run out of memory. Unusual MP4 layouts, external data references, encrypted media, edit lists and vendor-specific boxes have not been exhaustively tested. Treat output validation as structural validation, not proof that every player or social platform will accept every file.

The patch changes container layout, not the encoded image quality. “Fast start” is a playback-startup layout convention; it is not a TikTok compression bypass. TikTok may still transcode, resize, or recompress the uploaded video. Any improvement to posted quality is unverified and not guaranteed.

## Suggested validation before production

Test files generated by multiple encoders and verify playback in more than one player. Add automated fixtures for version-0/version-1 `mvhd`, `stco` and `co64`, files with boxes between `ftyp` and `mdat`, and malformed inputs. For robust large-file support, move parsing and patching into a Web Worker and implement streaming or bounded-memory processing.
